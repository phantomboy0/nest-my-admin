# M4-3 — Audit Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every change made through the admin is recorded with who, what and when, and a field-level diff (spec §10.2 audit log, Django `LogEntry`). This covers:
- records: created, updated, deleted, restored, purged;
- actions;
- settings-page saves;
- role, group and membership changes;
- sign-ins: success, failure, sign-out;
- view-as starts.

It can be read on a record's History tab and on an audit page, with field permissions applied to the reader. First consumer: shop-nest (who changed a price, a status, a setting).

**Architecture:**
- **Enabling it:** `AdminModule.forRoot({ audit: { retentionDays?: number } })` with `ADMIN_AUDIT_ENTITIES`. Without `audit`, nothing is recorded and the routes answer 404.
- **The `nma_audit` table** (`audit/entities.ts`, `NmaAuditEntry`):

  ```
  id (bigint, increasing), at, actorId?, actorName?, viewAsBy?, event, resource?, recordId?, recordTitle?,
  changes (json: Array<{ field, before?, after? }>), meta (json: { action?, input?, ip?, userAgent?, page? }), correlationId
  ```

  Indexes: `(resource, recordId, id)`, `(actorId, id)`, `(at)`.
- **Events:**
  - `{r}.created`, `{r}.updated`, `{r}.deleted`, `{r}.restored`, `{r}.purged`, `{r}.action.{name}`;
  - `page.{name}.updated`;
  - `rbac.role.changed`, `rbac.group.changed`, `rbac.user_roles.changed`;
  - `auth.login`, `auth.login_failed`, `auth.logout`, `auth.view_as`.
- **Recording record writes** (`audit/audit.service.ts`, `AdminAudit.record(entry, ctx)`): `AdminApiService` already serializes records, so the diff is computed generically. That covers host overrides too.
  - **update/action:** the serialized record before (`record(entry, existing)`) and after → changed top-level fields. Objects and JSON are compared as JSON; relation refs by id; file fields by key.
  - **create:** after only. **delete/purge:** before only. **restore:** no changes.
  - The entry is inserted **with `ctx.manager` inside the write transaction**, so a rollback discards it and a committed change always has its entry.
  - Bulk runs write one entry per record.
- **Masking at write time:**
  - fields marked `sensitive: true` (new `fields` option; `password`-widget fields are sensitive automatically) are stored as `{ field, changed: true }` with no values;
  - settings-page secret fields likewise;
  - action `input` is stored with sensitive and secret keys removed.
- **Masking at read time:** a reader sees `before`/`after` only for fields they can view in that resource (field rules, `restricted`); other changed fields show as `{ field, hidden: true }`.
- **Auth and RBAC events** are recorded where they happen:
  - `AdminHttpServer` around `POST`/`DELETE /api/session`: `login_failed` carries the attempted username, never the password;
  - `viewAs()` replaces the hourly log line with an entry;
  - rbac routes inside their transactions, recording role permissions before and after.
- **Reading:**
  - `GET /api/resources/:r/:id/history?before=<id>`: needs view of the record (scope included), as for GET. 50 per page, newest first.
  - `GET /api/audit?actor=&event=&resource=&record=&from=&to=&before=<id>`: needs the global code `audit.view` (added to the catalog when audit is on). Entries of resources the reader cannot view are listed without `changes`.
  - Keyset paging by `id`.
- **Retention:** when `retentionDays` is set, an unref'd daily timer deletes entries older than that, in batches of 1000.
- **Events for host code** (`@OnAdminEvent`) are not part of this plan; the audit table is the record. Hosts that need hooks keep calling their services from overrides.

**Deferred:**
- `source: 'all'` (a TypeORM subscriber auditing writes made outside the admin);
- field revert from the History tab;
- exporting the audit log;
- `@OnAdminEvent`.

**Spec:** §6.5 (view-as audited), §8.3 (event names, actor and diff), §10.1 (`LogEntry` parity), §10.2 (audit log: field-level diffs, field permissions and scopes, sensitive masking, auth and permission-change events, retention pruning). Plan 3 of 3 for M4 (shop-nest spec §9).

## Global Constraints

- All earlier constraints apply.
- **A sensitive or secret value is never stored in the audit table**, not even hashed.
- **An entry exists if and only if its change committed.** It is written in the same transaction.
- **Reading the audit never reveals more than the reader could see on the record itself.**

## Review Focus

1. **A write that rolls back** (the resource throws after a flush) leaves no audit entry; a committed write always has one. Test in Task 1.
2. **A reader with `audit.view` but a `hidden` rule on `salary`** sees `{ field: 'salary', hidden: true }` on both the History tab and the audit page. Test in Task 2.
3. **History of an out-of-scope record** → 404 (the same as GET), even when the reader authored entries for it before their scope changed. Test in Task 2.
4. **A failed sign-in** stores the username and IP but never the password or OTP; a burst of failures cannot slow sign-in. The insert uses the auth's own connection and is not awaited for the response. Test in Task 1.
5. **A host `update` that changes fields the DTO did not send** (computed totals) is diffed from the reloaded record, so those changes appear too. Test in Task 1.

Consumes M4-2 actions and pages for their events.

    - a settings save masks secrets;

    - login, failed login (no password, Review Focus 4), logout and view-as;
