# M4-4 — Inlines and Host-Registered Files Implementation Plan (v0.3.0)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- **Inlines** (spec §5.2 `{ section, inline: ChildAdmin }`, §6 "scopes apply to … inlines", §9 "inlines as stacked cards", Django's `TabularInline`/`StackedInline`): a parent's form shows and edits its child records — a product's variants, pictures, specs and FAQs; an order's lines — and one Save writes the parent and every child change in **one transaction**.
- **Host-registered files** (requested by shop-nest, owner's decision 2026-10-14): a host that stored a file itself (an image fetched from another system, an attachment taken by its own API) records it in `nma_file` against a record's file field, so `AdminFiles`, the admin's downloads, `_files` and the delete/purge lifecycle treat it like an upload.

First consumer: shop-nest plan 3 (catalog): `Product` with inlines for `Variant`, `ProductMedia`, `ProductAttributeValue` (attribute and option pickers that depend on the product's category), `ProductExtraSpec`, `ProductFaq`, `ProductWarranty`.

**Architecture:**

- **Declaring an inline.** A child is an ordinary resource (`@AdminResource(Variant, …)`, its own permissions, scopes, fields, DTOs, hooks and service overrides). The parent's layout places it:

  ```ts
  form: FormConfig = {
    create: CreateProductDto, update: UpdateProductDto,
    layout: [
      { section: { fa: 'مشخصات', en: 'Details' }, fields: ['name', 'slug', 'categoryId'] },
      { section: { fa: 'تنوع‌ها', en: 'Variants' }, inline: VariantAdmin, display: 'table', order: 'sort', min: 1, max: 200 },
      { section: { fa: 'تصاویر', en: 'Pictures' }, inline: ProductMediaAdmin, display: 'cards', order: 'sort' },
    ],
  };
  ```

  - `inline` — the child resource class. It must have exactly ONE to-one relation (many-to-one, or an owning one-to-one) whose target is the parent's entity; that relation's field is the **link field** (`productId`). It may name it with `link: 'productId'` when there are several. Boot check otherwise.
  - `display: 'cards' | 'table'` (default `cards`: stacked cards with the child's form layout; `table`: one row per child, one cell per field in `fields` order — for short rows like variants).
  - `fields?: string[]` — which of the child's form fields the inline shows (default: the child's update form fields minus the link field). Fields not shown keep their stored values (and their DTO defaults on create).
  - `order?: string` — a numeric field of the child that the UI's drag/up-down writes as 0, 1, 2… and that rows are read sorted by (then by primary key). Without it rows are read by primary key and cannot be reordered.
  - `min?: number`, `max?: number` (default `max: 100`, hard cap 500) — enforced on the server after the save's changes are applied (count of rows that will exist), as a 422 on the inline.
  - `label` comes from the section; `name` of the inline in the API is the child resource's `name`.
  - A child may be inlined into more than one parent (different link fields). An inline may not contain inlines (one level; boot check). The link field is never shown or writable inside the inline.

- **Schema.** `ResourceSchema.form.layout` gains `FormLayoutInline { inline: string /* child resource name */, label, display, fields, order?, min?, max?, link }`, and the schema response carries `inlines: Record<childName, ResourceSchema>` — each child's schema CUT BY THE POLICY for this user (fields, constraints, permissions `{ view, create, update, delete }`). An inline whose child the user cannot `view` is left out of the layout entirely (as if not declared). View-as: read-only as everywhere.

- **Reading.** `GET /api/resources/:parent/:id` returns `_inlines: { [childName]: { rows: Record[], total: number, truncated: boolean } }` — the child records whose link equals this parent, through the CHILD resource's own read path (`findMany`/`buildListQuery` with its `query()`, scopes and field cuts, `_files`, `_perm`, `_readonly`), sorted by `order` then primary key, at most `max` rows (`truncated` when more exist — the UI then links to the child's filtered list instead of editing). One query per inline, not per row. Creating a parent: `_inlines` is empty.

- **Writing** — one request, one transaction. `POST /api/resources/:parent` and `PATCH /api/resources/:parent/:id` accept, next to the parent's fields:

  ```json
  { "name": "…", "_inlines": { "variant": {
      "create": [ { "_key": "n1", "sku": "A-1", "price": "100000" } ],
      "update": [ { "_id": "17", "price": "120000" } ],
      "delete": [ "18" ],
      "order":  [ "17", "n1", "19" ] } } }
  ```

  Inside the parent's `write()` (the same `ctx.manager`, write participants — files, audit — for every child write):
  1. The parent is created/updated first through its own resource method (unchanged; a parent with only inline changes runs no parent update and gets no parent audit entry).
  2. For each inline, in layout order: **deletes**, then **updates**, then **creates**, each through the CHILD resource's own `delete`/`update`/`create` (so host overrides, hooks, services and `@AdminCan` apply), with the CHILD's policy: `{child}.delete|update|create` required (403 for the whole save, nothing applied), each `_id` must belong to THIS parent and be inside the user's scopes for that operation (else 404 for the whole save). Creates get the link field set by the server to the parent's id (a link value sent by the client is refused, 422). Updates may not change the link.
  3. `order`: when the inline has `order`, the server writes `0..n-1` into that field for the ids listed (existing rows by `_id`, new rows by their `_key`); the list must be exactly the set of rows that exist after the save (422 otherwise).
  4. `min`/`max` checked on the resulting count.
  5. Any failure rolls back everything (parent included). Errors keep the existing format with dotted paths: `_inlines.variant.create.0.price`, `_inlines.variant.update.17.price` (by `_id`), `_inlines.variant` for count/order errors. A 409 version conflict on the parent works as today; children with `@VersionColumn` send their version in the update entry (`_version`) and a mismatch is a 409 naming the inline row.
  - Validation of each child entry uses the child's create/update DTO exactly as its own endpoints would (whitelist, partial update, file fields resolved through the files lifecycle — uploads in an inline are tokens like anywhere else, attached to the CHILD record).
  - Limits: at most 500 entries per inline per request, and the existing JSON body limit.
  - Nested inlines are refused (422) if sent for a child that has none declared.

- **Dependent options with the parent's values.** `relationOptions(field, qb, ctx, values)` of a child used inline receives `values._parent` = the parent's values as the user sees them (form values in the picker; body-over-stored on save), so `ProductAttributeValueAdmin` can limit `attributeId` to the attributes of the product's category, and `optionId` to the chosen attribute's options. The picker request carries the parent's values (`?values=` JSON already exists; it gains `_parent`). Relation existence checks on save use the same values.

- **Audit.** Every child write is recorded as the child's own `{child}.created|updated|deleted` entry, in the same transaction, with `meta.parent: { resource, recordId }`; the parent's History tab also lists its children's entries (read path filtered by `meta.parent`, masked by the child's field rules, out-of-scope children as anonymous entries).

- **UI.**
  - `app/inline-section.tsx`: renders an inline section in the parent form — `table` (rows with cells using the existing field inputs, horizontal scroll on phones) or `cards` (stacked cards using `FormLayout` for the child's fields); add (if `create`), remove (if `delete` and the row's `_perm` allows; a new row is simply dropped), reorder by drag and up/down buttons (if `order`), per-row read-only fields (`_readonly`), per-row errors from the dotted paths, `min`/`max` shown and enforced client-side.
  - The parent form's dirty state, the unsaved-changes guard, ⌘S, Duplicate (children are NOT duplicated in this version — say so on the Duplicate button's confirmation), view-as read-only and the upload gate (a form does not save while an inline row is uploading) all include the inlines.
  - Saving builds the `_inlines` payload from the diff (only changed fields of changed rows; `order` only when the order changed).
  - `truncated` inlines are read-only with a link "N more — open the list" to the child's list filtered by the parent.
  - Texts in `en`/`fa`.

- **Host-registered files** (`AdminFiles`):

  ```ts
  register(input: {
    resource: string; field: string; recordId: RecordId;
    body: Readable | Buffer; name: string;
    visibility?: 'public' | 'private';   // default: the field's configured visibility
  }, manager?: EntityManager): Promise<AdminFile>
  release(input: { resource: string; field: string; recordId: RecordId; key: string }, manager?: EntityManager): Promise<void>
  ```

  - `register` checks the resource and field exist and the field is a `file`/`image` field (or rich text images? — no: file and image fields only), sniffs the type from the bytes and applies the field's `accept` and `maxBytes` exactly as uploads do (422-style `AdminValidationError` on refusal), stores the object under a key in the documented format, and writes an `attached` row for `(resource, field, recordId)`. With a `manager` the row is written in the caller's transaction and the stored object is deleted if that transaction rolls back (same mechanism as uploads); without one the row is written immediately. It does NOT write the key into the record — the caller stores the returned `key` in its column (inside the same transaction).
  - `release` deletes the row and, after commit, the object — for a key the record no longer holds. Releasing a key that is not attached to that record/field is a no-op (never deletes someone else's file).
  - Settings pages (`page:<name>` owners) are supported as `resource`.
  - Works with `files.dataSource`.

**Deferred:** nested inlines; duplicating children with Duplicate; inline-level actions; editing more than `max` rows inline; registering rich-text images.

**Spec:** §5.2 (`inline:` in the layout), §6.2 (scopes apply to inlines), §9 (inlines as stacked cards), §10 (audit of every write). shop-nest spec §9 (admin for the catalog) and shop-nest `CLAUDE.md` "files the shop stores itself".

## Global Constraints

- All earlier constraints apply (permissions on every path, scopes, field cuts, audit iff committed, files lifecycle, view-as read-only, `.js` imports, no driver hardcoded in tests, i18n parity, logical Tailwind utilities, no AI attribution).
- **A parent save with inline changes is one transaction**: either the parent and every child change commit, or nothing does.
- **An inline never widens access**: a user can read, create, update or delete a child through an inline only if they could through the child's own resource, under the same scopes and field rules; and only children of THIS parent.
- **Nothing that worked in 0.2.x changes** for a resource without inlines, and the shape of every existing response is a superset (new fields only).
- Version **0.3.0** for all five packages.

## Review Focus

1. **A child `_id` of ANOTHER parent** (or outside the user's scopes) in `update`/`delete`/`order` → 404 for the whole save, nothing applied. Test in Task 2.
2. **A save where the 3rd of 5 child creates fails validation** → 422 with `_inlines.<child>.create.2.<field>`, and neither the parent change nor the first two creates are stored; uploads attached in that request are back to temp. Test in Task 2.
3. **A user with `product.update` but without `variant.delete`** → the inline offers no remove, and a crafted delete is 403 with nothing applied. Test in Tasks 2 and 3.
4. **`relationOptions` with `_parent`**: the picker for a child's field narrowed by the parent's unsaved form value (the category the user just picked), on the picker request AND on save. Test in Task 2.
5. **`register` from a host for a file the field would refuse** (a PDF into an image field, over `maxBytes`) → refused, nothing stored; a registered file in a rolled-back transaction leaves no object and no row. Test in Task 4.
