# M3-3 — Roles, Groups and Users in the Admin Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permissions are managed in the admin itself (spec §6.6–6.7):
- roles are stored in the database next to the code roles, which are synced at boot and marked system;
- groups of users hold roles;
- users get roles directly and through groups;
- a Roles page with a matrix of resources × operations that expands to fields and scopes;
- Groups and Users pages (users come from the auth adapter);
- anti-escalation;
- export and import of roles as JSON.

**Architecture:**
- **Tables owned by core** (D3), opt-in with `AdminModule.forRoot({ rbac: {} })` and `ADMIN_RBAC_ENTITIES` in the host's DataSource (a boot error when missing):
  - `nma_role`: name, label, description, `system`, and `definition` as JSON: permissions, fields, scopes;
  - `nma_group`: name, label;
  - `nma_group_role`;
  - `nma_group_member`: user ids are strings, since users belong to the adapter;
  - `nma_user_role`.
- **System roles.** `forRoot({ roles })` are upserted at boot with `system: true`: their definition always comes from code, and the UI cannot edit or delete them.
- **Effective roles** of a user are the union of:
  - `resolveRoles` (options and adapter);
  - direct roles in `nma_user_role`;
  - roles of the user's groups.

  `AdminPolicy.forUser` reads them through `AdminRbac`, which caches per user and invalidates everything on any RBAC write (`permissionsVersion`, a counter in memory; one process in v0.1, the follow-ups note multi-instance).
- **Stored definitions** are validated with `checkRoles` when written (422 with the message). A stored role that stops matching the code (a resource renamed) is skipped at runtime with a warning, never a boot failure.
- **Management permissions:** global codes `rbac.view` and `rbac.manage` (superusers have them).
  - **Anti-escalation** (spec §6.5), for anyone who is not a superuser:
    - a role you create or edit may only grant what you hold yourself (every code its patterns match, field levels, scopes no wider than yours);
    - you may assign only such roles, to users and groups;
    - you may not change superusers or make anyone a superuser;
    - you may not assign roles to yourself.
- **Users** come from optional adapter methods:
  - `listUsers({ search, page })`, `getUser(id)`;
  - `createUser`, `updateUser` (displayName, email, isActive, isSuperuser);
  - `setPassword(id, password)`.

  The built-in adapter implements them, and setting a password ends that user's sessions. Custom adapters without them get a users page with role and group assignment only, for users that have signed in before (their ids appear in memberships).
- **API** (`/api/rbac/*`):
  - `GET/POST/PATCH/DELETE roles`, `GET roles/export`, `POST roles/import`;
  - `GET/POST/PATCH/DELETE groups` with `roles` and `members`;
  - `GET users`, `GET/PATCH users/:id` (`roles`, `groups`, and the adapter fields), `POST users`, `POST users/:id/password`;
  - `GET rbac/catalog`: resources with fields, scopes and custom codes, for the matrix.
  - Every write is checked against anti-escalation before anything is saved.
- **UI:**
  - The sidebar gets an "Administration" section (Users, Groups, Roles) for `rbac.view`.
  - Roles: a list, then an editor:
    - label and description;
    - the matrix: each resource × view/create/update/delete/purge as checkboxes, with a resource row that expands to per-field levels (hidden/read-only/edit) and scopes per operation;
    - custom codes;
    - global codes.
  - System roles are shown read-only. Export downloads JSON; import takes a file.
  - Groups: name, label, roles, members (a user picker).
  - Users: a searchable list with active and superuser badges; the editor has profile fields, roles, groups and "set password".

**Deferred to M3-4:** permission debugger, view-as, TOTP 2FA, `@nest-my-admin/testing`, configurable table prefix.

## Global Constraints

- All earlier constraints apply.
- **Fail closed.** A role row that does not parse or validate grants nothing, and a membership naming a missing role is ignored with a warning.
- **One path for permissions.** Every RBAC write goes through `AdminRbac` (validation, anti-escalation, cache invalidation). Nothing writes the tables elsewhere.
- **Opt-in.** Without `rbac`, M3-2 behaviour is unchanged and the Administration section does not appear.

## Review Focus

1. **Anti-escalation cannot be bypassed.**
   - Through the API, a non-superuser manager can neither grant nor assign more than they hold.
   - They cannot touch superusers, cannot make anyone a superuser, and cannot give themselves roles.
   - This covers wildcards (`*` in a role they edit) and field levels and scopes wider than theirs.
2. **Changes apply at once.** Assigning, removing or editing a role changes the user's next request (cache invalidated).
3. **System roles** are always code's: a UI edit is refused, and a changed code role replaces the stored one at boot.
4. **Import** validates like the editor (unknown codes and escalation included) and is all or nothing.
